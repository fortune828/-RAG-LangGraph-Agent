## 3. 方案与实际系统的冲突及建议

### 3.1 产品口径及 Prompt 基线需要更新

EVAL_PLAN 中 P2=v5、P3=v5.1 已过时；本轮已到 v14。建议确认后将 P2 冻结为本轮最终提交的 SYSTEM、ROUTER、RISK_SYSTEM **和动态上下文规则**，P3 只能由开发集失败驱动，P1 也必须保留同样输出与来源约束。提示词实验最后再做，本轮不增加三套运行。

评分必须覆盖午饭、理发：有实际卦意、篇幅相称、给具体建议；顺遂时自然鼓励，警示时贴切提醒，不渲染危险。不能奖励完全与卦无关的回答，也不能靠多贴引文拿高分。出处查证、风险支持及新聊天操作提示有各自任务边界，不能要求它们硬解卦。新话题须新聊天重起卦，旧“同卦继续换题”的标准不能沿用。

### 3.2 对照命名不一致，不能悄悄改变完成定义

| EVAL_PLAN | 现有 SPEC / tasklist | 建议处理 |
|---|---|---|
| W1：规则补检索 Workflow | C | 同一组，核心工程基线 |
| W2：受控 Agent | D | 同一组，直接使用生产图 |
| W3：人工充分证据 | 旧文档无同组 | 仅用于失败诊断，单列，不计端到端成本优劣 |
| 无对应组 | B：仅固定证据 | 首批 W1/W2 冒烟无需增加 B；完整 T10/T12 仍要求 B/C/D，未经确认不删除 B 的交付要求 |
| A0：只有问题的裸模型 | A：已知程序卦象但无检索 | **不是同一实验**；首轮可暂缓，不能把没有卦象的模型直接拿来评同卦关联或规则正确率 |

建议报告同时标注 W1/C、W2/D，确认后统一规划命名。生产只保留原图，不新建 Workflow 服务。W3 证据须真实存在并遵守所问对象；语料本就缺失的案例不可编造“充分证据”。W3 是诊断，不能保证质量一定达到上界。

### 3.3 检索对照必须准确说明改变了什么

- “现有基础检索”已经是 BM25 + phrase boost，不能原样把它同时命名为 R1 和 R2。建议 R1 为简单双字组重合计数，R2 为 BM25；两者共用文本归一化、字段、短语加分规则及稳定排序，只比较词项权重。R3 在 R2 上加入用户声明的业务元数据过滤。配置中写出参数和短语加分，避免称为纯 BM25。
- 只在隔离的检索实验中消融业务过滤；**服务端授权范围始终保留**，不得为了 R2 对照而放开生产 `allowedHexagramIds`。业务卦号筛选与硬授权范围分别记录。
- 当前 `SearchArgs` 支持卦号、作者、作品、版本、知识层和 anchorIds，**没有 sections/lineIndices**；爻位/章节精确问题走 `get_passages` 或既有 anchor。先按现有能力评分，不为方案字段增添生产接口。
- 搜索默认 topK=4，正式 Recall@5 应显式设置 5。精确查找单报；知识库确实缺失的案例不进入非空 gold 的召回分母，另评缺失识别。替代证据组不能把所有可替代 ID 都误当作必须全部召回。

### 3.4 必要检索标签取决于实际可用信息

`prepare → initial_evidence` 已固定读取原典，并按问题排序、选择部分注解，还可复用前两轮的证据。**工具调用为 0 不等于没有检索**。例如历史朱熹九二题无需工具，也可能已经获得足够注解。

标注前须冻结并核对 `availableEvidenceIds`，再确定是否必须补检索。可回答但语义错误，与缺证据没有检索，是不同失败。空结果也不天然是无效调用：未知出处的合理探索可返回空；“本可避免”“无必要”需要标签或人工判定。

应区分：模型提出的工具请求、消耗尝试预算的请求、实际执行成功/空结果、被程序拒绝的请求。当前 trace 的 step=tool 也包含拒绝记录，不能全部记成成功执行，更不能把被拦截的越权尝试当作权限泄露。

### 3.5 Workflow/Agent 比较的混杂因素

- 当前 W2 也是混合流程：普通首次直接生成、确定缺失或风险走固定分支、追问才路由。报告要分场景，不能把所有题都称为自主 Agent 决策。
- 同一份检索 API、初始证据、证据预算、模型、生成/修复提示词、校验、最大尝试数；W1 用规则解析明确目标、补齐缺口、对出处问题抽取已知短句/关键词检索，不能把 W1 设计为完全不允许补检索。
- 路由同时负责隐含换题识别，它不是纯检索策略。核心“检索决策收益”先在同题子集配对；显式换题和风险共享既有分支。隐含换题单独报告为路由能力，不能把它的收益全部归因于 RAG。
- 固定输入对照中，同一 case 的问题、卦象及历史一致；端到端多轮若各组接续自己的回答，历史自然分化，应单报会话效果，不再声称输入完全相同。两类结果不可混算。
- 首次读取、分词/索引缓存会影响耗时；需记录冷/热条件、交错运行两组，不总让一组先跑。实际 API 模型可能更新，配置与输出可追溯不等于字节级确定重现。

### 3.6 统计与语义盲区

- 当前校验检查归一化引文匹配及部分显式归属，不等于语义忠实。“有一条正确引用”仍可能夹带另一条无依据解释。
- EVAL_PLAN 只拆 interpretation 不够：summary 和 reflection 中也会泄漏传统断言、卦象事实或用户心理，须一并人工检查。承接已支持的卦意类比不必机械补引用，但不能藏进新断言。
- 过度拒答不能只数 `insufficient`；`answered` 中回避问题、反复声明不能决定也可能是拒答式行为。业务确实缺资料不算失败，技术 fallback 不算正确资料不足。
- “Schema 首次有效率”“一次修复后的最终有效率”“引文机械有效率”分开。各项分母含义固定，失败、预算中止、未执行单列，N/A 不填 0；总体均值之外报告分场景及配对胜/平/负。
- 明确计数单位：建议 40+40 计为待评分的固定输入轮次，另报独立会话/衍生组数量，整组划分；旧 tasklist 的“场景”可能含多轮，确认后统一，不能用轮次数冒充独立样本数。少量复跑报告每次结果，不能只留最好一次。

## 5. 哪些指标能自动做，哪些需要人

| 指标 | 自动化边界 |
|---|---|
| 规则映射、cast 保持、请求幂等、恢复、预算上限 | 已有测试可直接自动验证；报告明确测试输入与计数 |
| Schema、逐条引文 ID/归一文本匹配、显式元数据过滤 | 可自动；首答/修复后分开；不能替代含义判断 |
| 请求次数、工具各状态、重复/非法/越权尝试、耗时、已报告 tokens | 可自动；须补完整失败采集、未知值和固定检索的计时口径 |
| Recall/Hit@5、证据组覆盖、必要补检索触发/遗漏/避免率 | **先人工标注 gold、充分证据及必要性**，再自动算；未标注不纳入分母 |
| API 成本 | 先有可靠 usage 明细及固定价目表再估算，明确失败/未知费用和缓存条件 |
| 引文语义支持、解释准确、卦意与处境连接、小事篇幅是否得当 | 人工逐条复核，包含 summary / reflection 中的传统断言；无法判断单列 |
| 实际回应、编造条件、过度拒答、命令式措辞、凶辞恐吓/保证未来 | 人工判断；状态码和关键词最多帮助定位，不作为最终判分 |
| F1/F2 区分度及任务成功 | 按独立 rubric 人工评分，再与机械硬条件汇总；不能让不同卦必须得出相反建议 |

首轮维持 0–2 分和“支持/部分支持/不支持/无法判断”即可，不建立模型裁判服务。不具备领域把握的句子标为无法判断；只有实际参与评分的人才能登记为人工评分者。可先由用户试评小批，重点/分歧样例若有第二位评审再做双人复核，未做就明确未做。

## 6. 待确认的最小实施路线

### 步骤一：用 12–16 条开发输入打通采集和 W1/W2

复用现有案例与 `session_for/history`，建立稳定 case/group/pair ID 和固定历史；覆盖日常小事、复杂选择、同题纠正、确需补检索、已有证据、未知出处、确实缺失和风险。标签文件独立于模型输入，读取后检查不会进入 Prompt。已见案例只作开发集，不移动到 holdout。

扩展现有 `backend/evaluate.py` 的执行和预算能力，复用 development_checks 的场景，不再建设另一个框架。先用标准库 JSON/CSV 和简单函数保存 manifest、调用记录、逐例结果；现有开发冒烟保留原用途。

W2 直接 `build_graph`。W1 只需在现有图的路由决策处增加一个可注入的小函数/分支，复用 prepare、tools、generate、validate、repair 与 checkpoint。规则代码放在 evaluation 下，只读问题、上下文和同等证据，不读 gold；规则决策不伪装成付费模型调用。不复制三套图，不新增策略注册器，不用 fake LLM 冒充 Workflow 运行。生产默认始终走现有模型路由。

验收：相同固定输入能分别运行 W1/W2；需要和不需要检索均覆盖；原始输出、失败、修复、未知 usage 可回算；在下一次外部请求前阻止超预算。先模拟故障验证采集，再运行有明确调用/token 上限的真实开发冒烟。不输出“Agent 提升”结论。

### 步骤二：标注并跑检索层对照

从同一开发集整理结构化目标和自然语言查询，按当前发布集标注证据组及替代项、缺失状态。复用 `normalize_search/terms/lexical_index/rank_lexical/allowed`；只增加离线评分和简单 R1 排序，生产检索保持不变。显式 topK=5，输出 R1/R2/R3 与精确检索分表、分子分母及失败证据。

验收：任何 Recall/Hit 都可从 gold 和逐题命中重算；不把精确定位混成 BM25 成绩，不把范围放宽当性能提升。观察到召回瓶颈后再决定是否需要查询改写，初轮不引入向量库/Reranker。

### 步骤三：人工试评、冻结数据、扩大配对实验

先取 10–15 条开发输出试评，校准“有卦意且有帮助”、语义支持和拒答判据。随后补齐 40+40，按整个会话/衍生组划分并冻结哈希；在运行留出前停止按该集调 Prompt。核心为 W1/C 与 W2/D；B 的完整交付是否保留按用户确认的规划执行，W3 仅用于少量失败定位。

匿名打乱输出，评审材料保留问题、卦象、必要历史及原文依据，隐藏策略标签和工具 trace；评分结束再揭组。F1 用同问不同卦，F2 用同卦同问题、改变现实约束，不能仅用换成完全不同问题代替 F2。对不稳定/关键题重复运行，记录每次结果；报告总体、场景和配对差异及成本代价，不预设 W2 获胜。

验收：未执行、预算中止和无答案失败均保留；人工分数有理由和身份；两例失败具备复现输入、版本、原因证据和下一步；公开报告无需私有 runtime 或密钥即可核对。Prompt P1/P2/P3 暂缓到这些数据成立之后，避免首轮实验矩阵膨胀。

## 7. 当前最值得优化的问题

现有真实失败首先指向**生成时曲解用户动机、传统解释夹带无依据内容、同题追问重新展开无关卦义**，不只是检索不足。本轮已看到“证据和引文都正确，建议仍牵强”的实例。优先通过人工逐句审查与 W3 诊断区分：材料不充分、取义错误、类比过度、历史误读；不要先上更复杂检索或增加 Agent 节点。

下一阶段的第一交付应是“少量配对案例 + 完整记录 + 可重算表 + 真实失败原因”，而不是一个总分或预设的提升百分比。上述建设等待用户确认后开始。
