# 项目展示与面试说明 · 2026-10-10

这是一套 Python / FastAPI / LangGraph 驱动的《周易》情境对话系统。React 负责交互；程序完成起卦和会话固定性，检索提供可追溯原典与注解，模型负责理解问题和组织自然回答。它提供文化视角的讨论，不验证预测是否灵验。

## 可直接使用的简历版本

**《周易》知识增强对话 Agent｜Python、FastAPI、LangGraph、SQLite、RAG**

- 实现确定性起卦、固定会话卦象、受控工具调用与一次校验修复；基于1,076条版本化原典/注解进行中文BM25检索，结合作者、作品与卦爻过滤，对引用原文及显式归属实施服务端校验。
- 建立40开发+40独立测试、四策略共320输出单元的真实API对照，区分检索命中、引用匹配、语义完成与成本；生产混合策略独立测试机械完成38/40，P50/P95为19.31/28.13秒。
- 在6个预先标注的测试知识缺口中，规则流程取得齐备证据3/6，受控Agent及生产混合策略5/6；进一步追踪到其中1题证据被生成前过滤，实际可见齐备降为4/6，保留负面结果并定位链路缺陷。

数字均来自[正式报告](final-evaluation-20261010.md)及其可重算原始记录。38/40不能写作“回答准确率95%”；6题证据覆盖不能写作“Agent普遍提升33%”；320单元不是320独立用户。若简历空间有限，可只写前两条。

## 面试中如何解释关键设计

**RAG实际解决什么？**

它让模型拿到特定作者、版本、卦爻的可核对文字，减少依赖记忆逐字背引的需要，并能区分确实缺失与暂未获取。它没有自动解决文言误释或现代类比牵强。本轮把输入证据、输出claim与语义评阅分开，避免用引用匹配率冒充知识准确率。

**为什么没有使用向量数据库和Reranker？**

当前语料规模较小，来源结构明确；确定性按ID/元数据定位与中文双字组词面检索已经可运行并可解释。本轮R1/R2在14题非空测试参考上的Hit@5均10/14，未显示BM25在此小集的优势；元数据过滤提升返回材料纯度，同时降低对象覆盖。没有实验依据证明增加组件会提高用户回答质量，所以保留简单实现。这不是断言向量检索无价值。

**Agent和Workflow有什么区别？**

固定Workflow依据输入中可解析目标补证据，便宜且可预测；模型路由可解释模糊记忆、拆分不明确的需求，再选工具。生产采用混合策略：明确文献目标可确定性取证，其他适用追问保留模型判断。规则C不是“不许检索”的弱基线，B才是仅初始证据。独立测试C/D/H模型调用43/70/66次，成本与输出质量分别报告，不能用“工具更多”宣称更智能。

**为什么起卦和权限不交给模型？**

它们有明确可计算规则，应由确定性程序承担。模型不能重新计算卦象、随意扩大检索权限或虚构证据ID。相同会话固定卦象、请求幂等与持久化有测试；确定性程序保证的是实现契约，不证明古典解释或占卜结果真实。

**如何设计公平实验？**

冻结生产提交、知识发布、模型参数、输入和Rubric；同一题四组共用卦象、历史、初始证据、工具和生成/校验机制。按整个衍生组划分40+40，保存失败、修复及实际usage。另做memory/classic/full知识输入消融、离线R1/R2/R3与真实连续对话，分开报告，不将不同条件的成功率拼成总指标。

**怎样衡量自然交流？**

独立AI匿名评五维，记录具体理由与错误；16份预选输出双评，保留分歧。任务完成单列，无答案技术失败不参与五维平均但仍进入任务分母。真人评分包隐藏策略及AI分数，保持空白待用户填写。AI意见不称专家Gold，机械成功不称用户满意。

**最值得讲的失败案例是什么？**

开发dev-31和测试test-33：工具确实取到所需原文，但生成前按解析目标筛选时，只留下作者注解，原典被过滤。若只看检索Recall，会误判系统已有全部信息；若只看最终答复，又会把原因推给模型。将“取得/保留/生成可见”分层记录后才能定位。另一类是quote完全真实而文义/用户身份被误判，说明确定性引用校验的边界。

**当前还没有证明什么？**

没有证明Agent总体胜过有效规则、RAG普遍提高生活建议、模型解释达到专家水准或用户长期满意。价格是基于缓存usage的API估算，延迟是在四组并发条件下测得，不能承诺线上SLA。正式结果已用于分析，后续优化应把这些题转成已见回归，另立新独立测试。
