**检索与生成实际怎样工作**

```text
首次：用户困惑 → 程序计算并保存六爻
               → 固定取原典和少量相关注解
               → 模型依据证据解释 → 引用、对象和归属校验

追问：同一卦象 + 会话 + 既有证据
               → 模型判断是否需要另一解释角度或补充依据
               → get_passages / search_knowledge（最多 3 次工具尝试）
               → 带来源与覆盖信息的结果 → 生成 → 同一套校验
```

- `get_passages` 按卦、爻、章节、层次、作者、著作、版本和锚点精确取证。默认保留原典查询行为；取注解时使用 `layers:["commentary"]`。
- `search_knowledge` 增加简繁搜索归一、元数据过滤和词面排序。只转换搜索文本，展示和逐字引文保留来源文字。当前没有向量嵌入或语义检索模型，预留接口不等于已实现语义 RAG。
- 工具返回命中 ID、检索通道、来源版本、覆盖状态、缺失对象与截断情况，避免把“未入库”“没有召回”和“超出上下文预算”混为一谈。
- 引用校验支持逻辑位置与作者匹配，防止拿原典冒充某家注、拿另一卦或另一爻替代目标材料。“本库未收录某作者”可以如实说明，不应被误判成作者观点断言。
- 证据按预算组织，必要经文优先。长片段不截半句冒充完整注解，预算丢弃记录在 trace 中。该预算不是供应商精确 tokenizer。
- 新会话固定新知识版本；旧会话补记旧 release，保留原引用与同一六爻。不静默把旧证据替换成新版。
- 引用卡展示作者、著作、版本、层次、来源与核对状态。后端把来源元数据发给界面，模型只输出证据 ID，不负责生成来源网址。

归属与引文检查仍是有限规则：引用真实、作者正确，不保证一整段现实建议被引文支持。语义相关性、对注家观点的理解以及是否值得补检索，仍须单独人工审查和对照评测。

**运行、构建与回滚**

本次验收结束时，根代理已启动正式 3001 服务：健康检查为 configured=true、1,076 条证据、新 release，首页 HTTP 200。当前可直接打开 `http://127.0.0.1:3001`，无需再启动第二个进程。测试用 3002 临时服务已停止。

服务停止后，首次安装与开发运行仍为：

```bash

```

打开 `http://127.0.0.1:3001`。VS Code SSH 用户在“端口”面板转发远端 3001，并打开转发后的本地地址；运行终端保持打开。生产模式先 `npm run build` 再 `npm start`。已有会话沿用旧 release，要试用新注解请使用“新建起卦”。普通起卦仍随机，下面固定乾卦只用于评测。

```bash
npm run knowledge:build       # 从本地固定快照构建；不自动下载新版本
npm run knowledge:audit       # 来源哈希、版本与覆盖审计；不调用模型

npm run eval                  # 64 项原有精确检索契约
npm run knowledge:smoke       # 只列出 3 个场景及预算，不调用模型
```

`data/knowledge/active.json` 记录默认发布。旧包与新包都保留；不要在同一个 release ID 下修改正文。需要修正时生成新 release，再切换默认版本，并核对生成策略与对应覆盖信息。旧会话不能因默认版本变更而自动换资料。

**评测与费用边界**

新增确定性验证涵盖：经／注／疏分离、跨行括注与嵌套标记、作者过滤、逻辑位置、简繁检索和原文引文区别、来源哈希、缺失覆盖、版本保持、自然追问的工具执行链，以及固定版本和 Agent 版本共用修复校验。mock 工具测试验证程序能执行模型选择，不证明真实模型已经学会选择工具。

需显式执行以下命令才会运行收费模型：

```bash
npm run knowledge:smoke -- --live --max-calls=12 --max-tokens=60000
```

此命令固定乾卦九二动爻，依次运行自然首次问题、不点名注家的自然追问、未收录著作请求，真实续接会话。每次完成或失败立即保存答案、证据、工具轨迹、用量和版本。保存路径为 `evaluation/results/knowledge-smoke-<时间>.json`，不会覆盖历史报告。

全局最多 12 次模型请求。token 预算在发请求前按序列化 UTF-8 字节数、输出额度和协议余量保守预留，返回后按 usage 结算；缺失 usage 或请求失败保留该次预留。这不是模型官方精确分词或金额上限。预算不足停止并保存未运行状态，不把未运行算成功。

报告分别记录“检索到注解”“引用注解”“引用来自本轮工具的注解”。若已有资料足够且模型未调用工具，不自动判失败；若要证明 Agent 的实际补检索价值，应看真实工具新增了什么有效证据。`semanticSupportReview` 和 `attributionMeaningReview` 默认保持 pending，自动格式检查不能改成人工质量评分。

现有 `npm run eval:live` 的三版本评测已统一为 `shared-generation-validation-v3`：baseline 只给卦辞，evidence 用固定取证，agent 增加工具；三者使用同一生成约束、对象／归属／引用校验和一次修复。旧历史数值不得与新协议混算。旧“缺朱熹注”“恒彖缺失”样例的预期随当前覆盖更新；原 `cases.json` 中的 test 标签不代表独立冻结留出集。

浏览器检查默认使用 mock API，只验证页面引用元数据、刷新、同卦展示、删除和手机宽度，不产生模型费用：

```bash
BASE_URL=http://127.0.0.1:3002 \
CHROMIUM_PATH=/path/to/chrome \
npm run test:browser
```

每轮截图保存到独立时间戳目录，可用 `BROWSER_OUTPUT_DIR` 指定新目录；需要真后端运行须显式加 `--live`。建议测试服务使用临时 `DATA_DIR` 和独立端口，避免触碰已有会话。

续接问题为“假如以后开始承担管理责任，怎样避免因职位提高而自满？请从另一个阶段的角度帮我理解。”不点名注家、爻位或工具，仍由模型决定是否补检索，独立报告保存为 `knowledge-followup-<时间>.json`。该次真实续接也没有工具调用：2 次模型请求、15,828 tokens，返回 answered；已有九二注本身包含九五与上爻比较，因此不能只因问题换了角度就断定必须补检索。报告为 `evaluation/results/knowledge-followup-2026-09-26T08-57-53-116Z.json`，结果保留，不筛掉无工具样例。

`--resume` 另支持 `--question="..."` 传入最多 2,000 字的开发追问，仍不覆盖原报告。第三份实际运行将问题改为“如果从本卦上爻来看，为什么进得太过反而会有悔？我想用这个角度反思以后带团队的风险。”该问题不点名注家或工具，但明确要求本卦上爻。

该次暴露了真实失败：`evaluation/results/knowledge-followup-2026-09-26T08-59-30-393Z.json` 共 2 次请求、15,353 tokens，0 次工具调用，返回 insufficient。库中实际存在对应上爻原文与部分注解，因此这是**过度拒答**，不是正确识别知识不足，不能计为成功。原因是 router 在已有上下文缺少目标爻时提前给出 ready，随后生成阶段只能说明未获得该材料；原有引用校验能防止编造，却不能促使 router 补足已收录目标。

针对这个开发失败增加有限反馈：当明确目标实际已收录、但未进入上下文时，将缺口反馈给 router 再决策一次；不由后端静默代替模型取工具，也不对未收录材料反复检索。修复后的 Prompt／策略版本为 `evidence-agent-v3.1`；初始上下文增加缺失但可取得的目标元数据，错误 ready 后最多再反馈一次，正文仍须模型真实调用工具取得，不直接注入新证据。该题已参与调试，后续不能冒充独立留出题。
