默认 `deepseek-flash` 已开启 `thinking.type=enabled`、`reasoning_effort=high`。依据 [官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)，工具请求必须完整回传历史 assistant 的 reasoning_content；本项目原本保留完整 message，现以适配器测试及真实工具循环确认，不将该字段当作最终回答展示。

移除思考模式无效的 temperature；max_tokens 从 2200 调整到 8192，为推理和最终答案提供预算；HTTP 超时从 60 调为 120 秒，开发评测每场景仍以 150 秒为上限。预算预留同步采用新的最大输出限制，报告新增模式、effort、输出上限及模型适配器／配置哈希。当前 graph v6 / prompt v6，提示词与上轮不变。旧中断 checkpoint 沿用版本不兼容处理，避免缺 reasoning_content 的旧工具消息直接续跑；已完成历史可读。

## 对代码的原因分析

以下区分可由代码确认的机制与基于输出的归因推断，不把每次模型表现归结成唯一原因。

1. **真实历史不等于当前相关事实。** graph.py 的 generation_messages 把最近窗口的用户发言全部作为“对话事实”，没有标明哪些属于已结束话题。模型被要求使用这些事实，也被要求不带旧话题，两者的取舍完全靠生成时判断。换到家务问题时带入积蓄，是相关性筛选不足，不能只靠“不编造事实”解决。
2. **生成模型看不到自己已经讲过什么。** history 返回旧助手内容供路由使用，但最终生成只保留用户发言，同时每轮又可拿到相同经典材料。删除旧助手全文能减少污染，却也削弱了避免重复解释的依据。更强的模型仍不能知道被删去的旧回答。未来宜提供有边界的已答主题／简短上下文，不是恢复全部旧回答或禁止追问引用。
3. **历史预算计算与最终用途不一致。** history 的 6000 字符预算包含旧助手段落，最终生成却丢掉这些段落；旧回答越长，可带入的用户事实越少。遇到最近单轮已超过预算，还会直接 break。此机制确实存在，但不能据此声称每个当前失败都由截断导致。
4. **机械验证不检查语义支持。** validation.py 检查 ID、引文存在、kind、明确目标和局部归属；没有检查每一个解释断言是否由原文支持，也不检查相关性、重复或风险建议的具体程度。因此可以带真实引用扩展未经支持的解释，也可在 reflection 中给出过强结论并通过。kind 是内容分类声明，不是正确性证明。
5. **提示词要求多而取舍不够明确。** 既要求直接回应、传统解释、现实类比、具体建议，又要求避免重复和附必要限制；summary、正文、limitations 容易重复同一边界。风险提示没有完整界定在信息不足时行动建议应到什么粒度，因此模型可能从风险提醒扩写成仓位、期限或心理判断。需要缩减和澄清任务优先级，不等于越加规则越可靠。
6. **意图与检索是有边界的启发式。** classify 以书名号、作者名等字符串触发 source_request，可能把文化类比归为文献请求；出处范围同样靠有限表达识别。BM25 只做词面相关排序。更强模型可以在已有权限里选择工具，但不能修正服务端已固定的范围、目标和缺失判断。

建议优先修正上下文用途与相关性、给生成保留最少必要的已答上下文，再精简提示词取舍；用固定失败案例及成对样例验收。保留 LLM 自主决定生活追问是否引用，不增加分类服务、长期画像或自动评审框架。以上原因分析不代表这些后续改造本轮已经完成。
