**AI--main 简历就绪方案｜2026-09-26**

目标：把现有V2整理为一个能稳定演示、能解释设计取舍、能用可复查实验支持结论的第二项目。项目名称建议为“基于证据约束与工具调用的领域问答 Agent”。

本方案仅规划收尾工作，不启动实现或收费模型评测。依据为现有[V2交付记录](V2_DELIVERY.md)和[开发集评测](EVALUATION.md)，其中已有测试结果是历史记录，不代表本次重新验证。

**1. 本轮完成边界**

完成三项工作：稳定可用、知识可核对、实验可复查。保留当前六爻计算与双检索工具架构，暂缓八字、向量库、多Agent、知识图谱和微调。

现有16项测试、4096种六爻组合与64项检索契约检查继续保留。它们验证软件行为，不能代替回答质量评测。已有6个开发场景曾参与调试，不能再包装成独立测试集。

建议投入约7–10个有效工作日；这是按单人开发、每天数小时集中工作的安排估计，取决于语料审查和人工评分速度，不是交付保证。若时间紧，优先完成阶段A、B以及小规模但诚实的阶段C。

**2. 阶段A：先解决“别人能不能打开并使用”**

建议1个工作日。此前已经出现“无法使用”的反馈，先定位原因，再更新文档，不能仅用开发者机器上的成功截图代替验收。

| 任务 | 具体做法 | 交付物 | 完成标准 |
|---|---|---|---|
| 启动诊断 | 检查Node版本、依赖、端口占用、密钥是否配置、服务是否运行；错误不得输出密钥 | `scripts/doctor.ts`、`npm run doctor` | 缺密钥、端口占用等问题有明确说明 |
| 首次运行说明 | 分别写本机与VS Code SSH场景，明确3001端口转发和终端保持运行 | `docs/QUICKSTART.md` | 用户能按文档打开页面，不依赖口头补充 |
| 启动与恢复 | 保留单命令启动；检查刷新、模型超时、服务重启后的同卦重试 | 启动/恢复检查记录 | 失败不静默重起卦，不无限停留在加载态 |
| 演示回放 | 保存一份去标识的真实成功会话；必要时提供只读回放入口 | 脱敏演示样例 | 明确标记“历史回放”，不冒充实时模型生成 |
| 实际试用 | 由你在自己的浏览器完成首次解读、追问、引用查看与刷新 | 简短验收记录 | 全程能完成，失败原因可定位 |

真实模型验证只在显式运行检查命令时发生，不在每次doctor或启动时自动消耗额度。不要求为此部署公网服务、增加账户系统或容器集群。

**3. 阶段B：建立一个质量可控的知识子集**

建议1–2个工作日。先核对重点语料，避免宣称963条记录均为高质量知识。

1. 选择约8卦覆盖纯阴阳、上下卦变化和不同爻位；这是优先校对范围，不是只挑容易回答的问题。
2. 每卦核对卦辞、6条基本爻辞、大象和彖传，约72条；遇到缺失或异文明确记录，不凭模型记忆补全。
3. 检查字词、卦编号、爻位、章节、出处定位和版本是否对应；发现问题时保留修改前文本与来源。
4. 为条目设置 `review_status`、核对来源、核对日期、核对者与备注。代理辅助比对标成机器辅助，人实际复核后才标人工审查。
5. 对进入冻结测试集的全部目标证据进行同样核对；如果超出这8卦，增加对应条目的校对，不因方便而删掉难样例。
6. 明确学习语料与可公开发布数据的边界。现有上游限制不得通过更换项目许可证消除；若要公开完整仓库，先处理数据再发布，方案阶段不直接执行发布。

建议文件：`data/review/records.csv`、`data/review/corrections.json`、更新后的`data/SOURCES.md`。

`records.csv`建议字段：`evidence_id, source_version, reference_url, review_status, reviewer, review_date, issue, action`。

验收：演示必经条目及测试集所需目标证据有核对记录；缺失不会被填成虚构原文；报告准确给出已审核数量和未审核范围。不必为了第二项目投入大量时间做完整古籍校勘。

**4. 阶段C：建立真正可用的问答评测集**

建议2个工作日准备数据和评分规则。目标为80个问答/会话样例，按40个开发样例、40个冻结测试样例组织。已有24个对话场景可经审核后作为开发素材；已有64个查表测试保持为单独的软件检查，不计入80个问答。

| 类型 | 开发集 | 测试集 | 验证重点 |
|---|---:|---:|---|
| 已有证据足够的解释 | 8 | 8 | 回应问题，避免无意义检索 |
| 具体爻位/章节查询 | 8 | 8 | 读取准确对象，不能拿无关引用替代 |
| 出处查询与跨卦对照 | 6 | 6 | 工具选择、召回与出处对应 |
| 多轮追问与事实更正 | 6 | 6 | 复用卦象，处理用户更正 |
| 缺少材料与不支持任务 | 8 | 8 | 正确说明不足，避免编造或过度拒答 |
| 干扰指令与异常恢复 | 4 | 4 | 权限边界、失败重试与任务完成 |
| 合计 | 40 | 40 | 80个语义任务样例 |

异常恢复中的模型超时、非法工具参数等使用故障注入另做确定性检查；不要将这些无真实模型参与的测试与自然语言回答质量混算。

划分按问题来源和整段会话分组。同一问题的改写、同一会话的不同轮次不能跨开发集与测试集。测试集最好由未参与调参的人编写或保管；若只能自己完成，应写“冻结留出集”，不能称为独立第三方测试。

每条样例包含：

```json
{
  "id": "test-line-001",
  "category": "specific_passage",
  "split": "test",
  "lines": [7, 7, 7, 7, 7, 7],
  "history": [],
  "question": "本卦第二爻原文是什么？",
  "acceptable_evidence_sets": [["zy-1-line-2"]],
  "expected_behavior": "读取并引用乾卦九二原文；不得重新起卦",
  "tool_expectation": "required_if_missing_from_context",
  "unacceptable_behavior": ["引用卦辞充当九二原文", "重新抽样"],
  "review_status": "pending"
}
```

使用“可接受证据集合”，允许多个合理答案。不要给开放式反思问题强制指定唯一引文，只因模型没选某一句就判错。多轮任务保存完整用户消息、规范化会话状态和固定六爻输入；最终端到端多轮评测允许各版本产生自己的历史，标为整段会话实验，不与单轮模块消融混淆。

冻结前完成题目与标准审核，保存数据版本和哈希。冻结后不边看结果边调提示词；若确需根据测试失败修改策略，必须把该集降为回归集，并另准备新留出集。

**5. 阶段D：运行一次口径清楚的对照实验**

建议1–2个工作日。把现有“系统演进对比”和“单模块收益”分开，避免多个变量同时变化却把收益全部归给Agent。

| 实验 | 设置 | 可以回答的问题 |
|---|---|---|
| E0 基础版本 | 修正计算数据，只给卦辞；共同响应格式 | 原始知识供给有何局限 |
| E1 固定证据版本 | 完整固定取证 + 证据约束生成 + 校验，无动态工具 | 固定Workflow能覆盖多少任务 |
| E2 Agent版本 | 与E1保持生成及校验一致，增加工具决策与补检索 | 动态检索是否值得额外成本 |

E0→E1改变了证据和生成约束，只能称方案对比。E1→E2是主要Agent对照，控制相同模型、语料、六爻输入、生成参数、输出预算、校验规则和重试预算，允许并记录工具带来的额外上下文和调用。

如需要证明引用校验的效果，再仅在开发集比较“有校验/无校验”，不是默认增加第四组全量实验。

建议运行顺序：

1. 先对开发集中的5个场景跑3版本，检查协议、计分和用量。
2. 修复评测脚本问题，冻结代码与配置；人工检查指标是否奖励过度拒答或通用降级。
3. 跑40个测试场景×3版本，保存全部结果，包括错误和失败，不只保留最好的一次。
4. 在查看结果前预先选定每类1个稳定性样例，共6个，各版本再运行2次，单独报告三次波动，不把18次重复当成18个独立问题。
5. 进行匿名人工评分，完成结果表和误差归因。

主实验是120次“场景运行”，不是120次API调用；Agent和多轮场景可能触发多次请求。试跑后按实际平均tokens和调用数估算总量，配置每次实验的调用/token上限，超限停止并保存断点。需要金额预算时再核对届时价格，不在本方案预填金额。

所有版本均记录每例耗时、tokens、工具尝试、重试、终态、最终答案和证据。单独标记“未运行”“接口失败”“安全降级”“正确说明不足”，不合并为成功。

**6. 如何评分，以及哪些数字能写进简历**

| 指标 | 定义与计分方式 |
|---|---|
| 计算一致性 | 固定六爻输入与参考结果一致；继续使用独立规则测试，不让LLM裁判 |
| 证据召回 | 必需证据是否进入上下文；多种可接受集合中满足一种即可 |
| 引文真实性 | ID与原文匹配的引用数/全部引用数；同时报告无引用情况 |
| 证据支持度 | 被引用证据支持的可核验实质陈述数/应由证据支持的陈述数；逐条标出证据或缺口，不能只验字符串 |
| 可回答任务成功率 | 正确回答、证据支持且没有关键规则错误的任务数/可回答任务数 |
| 正确不足说明率 | 明确识别实际知识缺口的任务数/应说明不足的任务数；泛化报错或安全降级不计成功 |
| 过度拒答率 | 有足够资料却拒答的任务数/可回答任务数 |
| 同卦保持率 | 未经明确新建请求仍保持原计算结果的多轮会话数/对应会话数 |
| 无效工具调用率 | 重复、非法或无任务作用的调用数/全部工具调用数；空结果不自动等于无效 |
| 成本与延迟 | 全部运行tokens/成功任务数，并同时报告成功率；另给总tokens、平均调用数和耗时中位数，不排除失败成本 |

证据支持度中的“现代反思建议”与“原典事实”分开：原典事实需可核验，建议需标为解释，不能伪装成经典原话。开放式解释不评判是否“预测成真”。

人工评分表建议每个回答有：任务完成0/1/2、证据支持0/1/2、是否存在关键错误、错误位置、理由、审查者。模型可辅助指出疑点，不能冒充人工审核。

资源允许时，两人独立评分至少20%的分层抽样结果，报告一致情况并仲裁分歧；若只有你一人，隐藏模型版本、打乱答案顺序后评分，明确单人审查局限。对现有40条测试集应报告原始分子/分母，并给出不确定性说明；不把几个百分点的差异直接说成显著提升。

**7. 阶段E：准备3分钟演示和面试材料**

建议1个工作日。固定六爻值仅用于标记清楚的演示/回放，不让普通用户看到的随机起卦暗中使用预设结果。

| 时间 | 展示内容 | 要证明的能力 |
|---|---|---|
| 0:00–0:30 | 输入问题、展示程序计算结果 | 明确LLM计算边界 |
| 0:30–1:10 | 解读与可展开的原文出处 | 结构化知识和证据供给 |
| 1:10–1:50 | 追问缺少的某爻原文，展示真实工具轨迹 | 工具决策与反馈闭环 |
| 1:50–2:20 | 询问未收录材料，说明知识缺口 | 幻觉控制及停止策略 |
| 2:20–3:00 | 同卦恢复与一页实验结果 | 状态管理和验证能力 |

准备两三个可深入解释的失败案例，优先复用实际发现的问题：真实但无关的引用、出处查询被错误绑定到当前卦、合理不足回答被Schema拒绝、通用降级被评测误计成功。每个案例说明“触发输入→旧行为→原因→修改→验证→剩余边界”。

交付物：`docs/DEMO.md`、3分钟录像、1页架构图、1页实验表、`docs/FAILURE_CASES.md`。录像可以避免现场网络影响，但必须注明录制时间与版本。

建议能清楚回答以下面试问题：为什么首次用Workflow？工具具体改变了哪类任务的结果？为什么不默认上向量库？引用真实为何仍会幻觉？重试怎样避免重新起卦？测试集如何避免泄漏？Agent增加了多少调用？什么时候这个方案不值得用？

**8. 实施排期与分工**

| 时段 | 主要工作 | 依赖 |
|---|---|---|
| 第1天 | 启动诊断、远程访问说明、你实际试用 | 现有V2 |
| 第2–3天 | 重点语料核对、题目和评分规范 | 来源可查 |

| 第6天 | 冻结代码/语料/测试集，正式对照 | 评测脚本通过检查 |

助手可承担启动诊断实现、数据比对辅助、样例草案、评测脚本、运行与报告生成。你需要实际试用、参与确认领域资料和评分；能够找到熟悉领域且未参与调参的人复核，会比继续堆模块更有价值。若没有独立审查者，应保留这一局限，不伪造审核记录。

**9. 停止扩功能的验收标准**

以下是本项目的收尾门槛，不是行业通用分数线：

- 你能按文档从停止状态启动并完成完整演示，异常有明确处理路径。
- 核心计算、幂等、工具权限、同卦状态等确定性测试通过，没有已知阻断问题。
- 演示及测试所需目标原文有核对记录，未核对范围和数据用途限制写清楚。
- 留出集、冻结配置、原始输出和评分表齐全，任何报告数字均能回算。
- Agent在需要补充检索的子集上是否有效、额外成本多少，能用实验回答；没有收益也如实报告并缩小启用范围。
- 严重的伪造出处、静默换卦等失败需修复并回归；若参考测试集改动策略，不沿用原测试分数作为独立结论。
- 有稳定Demo、架构说明和至少两个真实失败分析。达标后先整理简历，不继续扩八字或模型训练。

不预设必须达到“95%准确率”或“降低50%幻觉”。样本规模、任务定义和标注质量比漂亮数字更重要。

**10. 简历表述模板**

完成后可写：

> 设计并实现基于证据约束与工具调用的领域问答Agent，结合确定性规则引擎、结构化知识检索和短期会话状态，支持可溯源回答与同一结果的多轮追问。
>
> 针对“引用真实但与问题不相关”等失败，设计对应证据检查、有限补检索与降级机制，覆盖4096种六爻组合及工具/会话异常验证。
>
> 在[N]个冻结留出任务上比较固定Workflow与Agent，需补检索任务成功数由[A/N]变为[B/N]，平均调用数为[X/Y]，并分析质量与tokens开销的取舍。

方括号只能填实际结果。若独立评测尚未完成，删除第三条的量化承诺，保留已经实现和验证的能力。
