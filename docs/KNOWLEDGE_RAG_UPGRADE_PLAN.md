**3. 知识结构：把“解释什么”和“谁在哪个版本里说的”分开**

建议保留文件式构建和本地服务，不先引入数据库服务。使用 JSON／JSONL 保存规范数据，构建时生成只读索引；当前规模先用内存 Map 与倒排结构即可。以后若规模、查询或启动耗时证明有必要，再换本地 SQLite 等存储，工具接口不变。

以下实体是数据结构，不要求逐个建微服务或数据库表。

| 实体 | 主要字段 | 作用 |
|---|---|---|
| `Work` 著作 | `workId, title, contributors` | 记录作品与作者／注者／疏者等角色；作品级贡献者不能替代段落归属 |
| `SourceSnapshot` 来源快照 | `sourceId, workId, editionLabel, url, upstreamRevision, fileHashes, rights, retrievedAt` | 固定电子来源、底本说明、取得方式与使用说明；未证实的底本写 unknown |
| `Anchor` 原典位置 | `anchorId, hexagramId, section, line, specialKey, chapterPath` | 统一表示乾九二等解释对象，不依赖某版标点与繁简 |
| `Passage` 证据片段 | `passageId, sourceId, layer, textOriginal, attribution, anchorIds, commentsOn, locator, review` | 保存可引用的具体版本文字及其解释对象 |
| `ReviewRecord` 审查记录 | `passageId, status, reviewer, checkedAgainst, date, issues, correction` | 区分机器解析、机器辅助比对、人工核对，不覆盖修改前材料 |
| `CorpusRelease` 发布清单 | `releaseId, passageHashes, sourceRevisions, parserVersion, indexVersion, coverage, legacyAliases` | 固定某次发布的内容、索引、覆盖范围与旧 ID 映射 |

具体规则：

1. **层次与章节分开。** `layer` 为 `classic / commentary / subcommentary / modern_editorial`；`section` 仍表示卦辞、爻辞、彖、大象、小象等。朱熹对彖的注解是 commentary，不能因为谈到彖就被当成原典彖传。
2. **位置与版本分开。** `zhouyi:01:line:2` 是逻辑位置；王弼注、朱熹注和不同底本经文各有自己的 `passageId`，共同关联这一位置，不互相覆盖。
3. **作者落实到片段。** `attribution` 区分直接署名、转引和未确定。孔颖达疏中引用王弼，不能把整段疏标成王弼原注；不确定的段落不进入要求精确作者归属的默认取证结果。
4. **允许跨对象注解。** `commentsOn` 为数组；一段比较九二与九五时可关联多个位置，并保留完整段落，不硬拆出失去条件的短句。
5. **保留特殊位置。** 普通爻位限制 1–6；用九／用六使用 `specialKey`。旧接口中的 7 仅由兼容适配器转换，不在新结构中宣称存在“第七爻”。将来收录系辞等通论时允许卦号为空，按篇章定位。
6. **原文与搜索文本分开。** `textOriginal` 保留所选版本文字；搜索字段另做简繁、标点与审定异体处理，记录规范化版本。搜索命中“潜龙”可以找到“潛龍”，展示与引用仍回到真实原文。疑似错字与版本异文不能都被自动“纠正”。
7. **出处可回溯。** `locator` 保存卷／章／卦／爻、原文件及定位；如有页标记保存其原值，但不冒充已核验的扫描页。字符偏移明确采用何种单位。清洗后片段须能映射回原始文件。
8. **版本不可漂移。** 可采用 `sourceId + snapshotRevision + segmentKey` 形成不可变片段 ID；正文修订产生新片段版本并保留旧记录。`releaseId` 则标记哪些片段版本共同构成本次知识库。

示意记录如下，仅表达结构，省略的正文和页码须从实际来源解析后填入，不能将此示例作为已审知识：

```json
{
  "passageId": "by-wyg@<snapshot>:qian-line2-comment-01",
  "sourceId": "by-wyg",
  "workId": "zhouyi-benyi",
  "layer": "commentary",
  "anchorIds": ["zhouyi:01:line:2"],
  "commentsOn": ["zhouyi:01:line:2"],
  "attribution": [{"personId": "zhu-xi", "role": "commentator", "kind": "direct"}],
  "textOriginal": "<从选定版本提取的完整注解段落>",
  "locator": {"chapter": "卷一·乾", "rawFile": "<快照内文件>", "pageLabel": null},
  "review": {"status": "parsed_unreviewed", "reviewer": null}
}
```

经文通常按卦辞／一爻／一段传文切分；注解按它所解释的经文单元及完整论述切分。长疏文可以保留父段与子片段关系，在检索命中后补相邻必要上下文。第一版不使用统一“每 500 字切一块”，也不让 LLM 凭记忆补缺文、作者或原典位置。

**4. RAG 设计：精确定位为主，词面补检索为辅，语义检索留接口**

沿用现有两个工具，不为每本书增加一套工具。扩展可选参数 `workIds / authorIds / layers / editionIds / anchorIds`；省略时兼容当前默认原典检索。底层把检索与模型工具定义解耦，首次 Workflow 和追问工具调用复用同一套 Retriever。

| 查询情况 | 处理方式 | 不能发生的行为 |
|---|---|---|
| “乾卦九二原文” | 锚点精确检索，限定 classic | 返回很相似的注解充当原文 |
| “朱熹怎么解释乾九二” | 锚点 + 著作／作者 + commentary | 因朱熹材料缺失而拿程颐注替代 |
| “王弼和朱熹对此有什么区别” | 分别取两家对应证据，再生成有归属的比较 | 只有一家材料却从模型记忆补另一家 |
| “这句话出自哪里” | 全库词面检索，支持简繁和可靠别名 | 默认把出处限定到当前起卦，漏掉其他卦 |
| “这对我目前的处境有什么启发” | 优先使用当前原典与已核对注解；必要时查询概念卡 | 把现代建议伪装成古人原话 |
| “查某本未收录的书” | 查覆盖清单并说明本库缺少相应材料 | 断言该书不存在或原作者没写过 |

拟议检索契约：

```ts
interface Retriever {
  fetchExact(query: ExactQuery, releaseId: string): RetrievalResult;
  searchLexical(query: SearchQuery, releaseId: string): RetrievalResult;
  // 仅预留：有失败样例和评测收益后再实现。
  searchSemantic?: (query: SearchQuery, releaseId: string) => Promise<RetrievalResult>;
}

interface RetrievalResult {
  hits: Array<{
    passageId: string;
    channel: 'exact' | 'lexical' | 'semantic';
    score: number | null;
    matchReason: string;
  }>;
  releaseId: string;
  missingTargets: string[];
  coverageStatus: 'covered' | 'partial' | 'not_ingested' | 'unknown';
  noHitReason?: 'no_match' | 'filtered_out' | 'ambiguous';
  truncated: boolean;
}
```

覆盖状态来自构建时发布的清单，检索状态来自此次查询，两者不能合并为一个空数组。例如“只入库了 8 卦的朱熹注”是覆盖局限；“已入库但没有召回”是检索问题；“返回结果被预算截断”是上下文问题。模型应表达对应原因。

词面检索第一步增加规范化、字段过滤、别名和倒排召回；可以把现有二字片段评分作为基线，再用相同样例比较 BM25 等排序。中文古文的切分规则必须固定并测试，不能认为换个索引库就自动获得中文语义能力。语义检索以后仅补充改写表达或概念查询，仍遵守作者／版本过滤，最终返回真实片段 ID。

证据组织采用明确的优先级：本次必须回答的原文与目标注家片段优先；其次是必要上下文；最后才是可选补充注解。普通首次解读先少量加入与动爻或主题直接相关的注解，不把三家整卦全文全部塞入 Prompt。按模型上下文上限设置证据预算与输出余量，记录被舍弃的片段；比较两家观点时保证两边都有材料，否则说明部分缺失。

**5. 接入现有 Workflow 与 Agent，不改变计算边界**

```text
首次解读
用户问题 → 后端确定性计算 → 固定取证策略
                              ├─ 原典精确读取
                              └─ 按问题／配置选少量对应注解
         → 组织带出处的证据 → LLM 生成 → 结构／引用／目标检查

后续追问
固定计算结果 + 会话 + 已有证据
         → LLM 决定是否补检索
         → get_passages / search_knowledge
         → 后端校验参数并执行 → 返回证据与覆盖信息
         → LLM 生成 → 同一套校验
```

首次“选择注解”仍可由确定性的查询解析与配置实现，不需要改成模型自由规划。不能确定用户说的注家或对象时先使用明确支持的范围，必要时请求澄清，不随意选择一种解释冒充用户要求。

需要同时处理的接入细节：

- **动态说明能力范围。** 当前 Prompt 和工具描述写死“没有朱熹注／现代注解”等。迁移后改由覆盖 manifest 提供可用著作、实际章节和审查范围；仅改数据而不改这些文本，会使模型继续错误拒答。
- **迁移目标校验。** `requestedEvidence()` 当前生成 `zy-1-line-2` 这类旧 ID。改成“目标锚点 + 内容层次 + 必需作者／著作”的要求，再匹配实际证据；旧 ID 经别名表解析，不能直接整体替换后留下失效规则。
- **校验出处归属。** 检查引文属于本轮证据、片段版本及元数据匹配。答案说“朱熹认为”时，所引证据须支持这一归属；第一版通过结构化引用元数据和限定输出规则减少错配，复杂转引仍需人工抽查，不能承诺纯规则全面判断语义。
- **分开原话、解释和建议。** 原文引用保留逐字核验；注家解释有作者标签；现代建议标明项目解释。真实引文仍可能不支持结论，证据支持度需要单独评测，不能以子串校验通过代替。
- **保留工具约束。** 沿用白名单、参数验证、次数上限、重复检测与停止机制。新资料中的指令也只是资料，不能改变工具权限或系统规则。在线运行只检索已发布本地语料，不增加任意网页抓取工具。
- **固定会话知识版本。** 新会话记录 `releaseId`，追问使用同一发布版本；旧会话保留已有证据快照，并绑定可回溯的旧 release。切换知识版本必须显式记录，不能把同一个证据 ID 悄悄换成新文字。
- **避免双份经典冲突。** 当前计算结果还带有静态卦辞字段；迁移时计算模块继续提供卦号、爻等事实，生成端经典引文以知识库证据为准，避免两份不同文本同时进入模型造成冲突。
- **引用卡可核对。** 在现有出处展示上补著作、注者／疏者、卷章、版本和核对状态即可；模型输出引用 ID，来源链接由后端解析，避免让模型生成网址。

同一爻各家观点不同不是需要消除的噪声。回答应分别说明“哪位注家、哪一版本、依据哪一段”，材料不足时只比较已取得的内容，不用多数投票产生一个所谓标准结论。

**6. 迁移方案：分批构建、兼容读取、验证后切换**

保留现有 `data/evidence.json`、`manifest.json` 和上游快照作为旧版回归基线。新数据在独立 staging 区构建，不直接覆盖线上数据。范围按“原典底座 → 多家注解试点 → 检索接入 → 扩量”推进。

| 阶段 | 工作内容 | 交付与进入下一阶段的条件 |
|---|---|---|
| A：来源与小样验证 | 每个候选保存来源登记；从乾等少数卦抽经文、爻辞和注解，试验经／注／疏分离，核对正文与署名 | 来源可定位；缺文、转引、解析歧义被显式标记；没有默认将整页归某位注家 |
| B：规范结构与兼容层 | 建 source/work/anchor/passage/release；将现有 963 条映射到新结构；建立旧 ID 别名；保留历史引用 | 旧 64 卦查表等契约不退化；既有引用仍能解析；审查状态不被批量升级为人工通过 |
| C：原典补缺与注解试点 | 核对原典关键字段，另源补恒彖并记录版本；试点 8 卦，例如乾、坤、屯、蒙、谦、豫、坎、恒；导入与目标问题有关的三家注解 | 每个进入演示／评测的片段有审核记录；来源、作者、对象和缺失范围可查 |
| D：检索和生成接入 | 扩展两工具过滤条件；增加覆盖状态、预算、动态 Prompt；改目标校验与出处显示；固定会话 release | 能正确回答已收录注解查询，并正确说明未收录对象；没有静默换卦、错注家、错版本 |
| E：冻结、对照与发布 | 在固定语料上对照检索策略；人工核对答案支持度；生成发布清单和回滚记录 | 所有结论能回到输入、证据、版本和原始输出；通过后再扩到更多卦 |

阶段 C 的 8 卦是深度审查和注解试点范围，不是把现有 64 卦原典删成 8 卦。原典目标是逐步形成明确版本、章节完整的 64 卦底座；此阶段不能宣称其余原典已全部人工审核。可先核对这 8 卦的卦辞、六爻、大象、彖共约 72 个位置，另加动爻小象、用九／用六和测试需要的材料。注解按完整论述导入，不为凑条数拆碎句子。

对需要人工辨认的经注混排，解析器先输出候选边界与错误清单；无法可靠确定的段落进入隔离区。不要为了全量自动化，在正文中把所有括号内容都一律视为某位作者的注解。网页清洗还须剔除导航、脚注按钮、序跋误混，并检测缺字占位符与异常断句。

建议新增的文件组织（仅规划）：

```text
data/knowledge/
  sources.json                  # 来源、底本、取得方式及使用说明
  works.json                    # 著作与贡献者
  raw/<source-id>/<revision>/    # 不可变快照
  staging/passages.jsonl        # 待审解析产物
  review/records.jsonl          # 校对、归属、修改记录
  releases/<release-id>/        # 发布片段、覆盖、哈希、索引、旧 ID 映射
scripts/knowledge/
  import-<source>.ts            # 按来源分别解析
  build.ts                     # 校验后构建发布包
  audit.ts                     # 完整性、定位、归属与覆盖检查
```

应用侧主要触及 `shared/types.ts`、`server/knowledge.ts`、`server/validation.ts`、`server/agent.ts`、会话存储版本字段与引用展示组件。计算引擎和现有服务路由不因本轮数据升级整体重写。构建与评测过程记录发布 ID、输入文件哈希、索引／规范化版本及代码版本；当前工作目录没有 Git 元数据，冻结时可先记录代码文件哈希，不虚构 commit。

切换时使用配置选择 `releaseId`，先在开发环境回放，再替换默认新会话版本。旧 release 暂留支持历史会话；出现引用映射或归属问题，切回上一 release 与匹配的 Prompt／校验配置。不能只回滚语料、不回滚依赖其字段的策略。

**7. 验证设计：证明知识与检索改善了什么**

沿用 [简历就绪方案](RESUME_READINESS_PLAN.md) 的开发／留出集原则，不把已有 6 个调试场景重新包装成独立测试。现有确定性检查和文档中的历史成绩，本次没有重新运行。

优先增加以下有实际失败风险的检查：

| 层面 | 具体场景 | 验收重点 |
|---|---|---|
| 解析 | 经注混排、跨页括注、疏中转引、序跋、缺文标记 | 原文和归属可复查；不确定内容隔离；来源片段可反向定位 |
| 精确检索 | 指定卦、爻、注家和著作；一次读取多个动爻 | 无错误作者替代、无静默截断；默认行为兼容 |
| 词面检索 | 简繁同句、卦名别名、未知出处、低相关问题 | 正确证据召回；没有默认锁死当前卦；无结果与覆盖不足分开 |
| 证据组织 | 原文与三家注解同时存在、长注预算不足 | 必要原文和目标作者不被无关高分材料挤掉；有截断记录 |
| 生成 | 两家观点比较、只有一家已收录、注家转引其他人 | 归属与证据支持正确；不编造缺少的一方 |
| 多轮与版本 | 同卦追问、服务重启、发布新语料后打开旧会话 | 计算结果不变；引用仍指向原发布版本 |
| 边界 | 材料里的干扰指令、伪造作者要求、工具非法参数 | 权限不扩大，错误可定位，不把降级计为成功 |

迁移后必须更新旧场景的预期：例如“朱熹注未收录”和“恒彖缺失”一旦不再成立，就不能继续把拒答算成功。对于只覆盖部分卦的注解，同时保留“范围内应回答”和“范围外应说明不足”的样例。

对照实验分两类，不能混淆归因：

1. **知识供给收益：**旧原典库与新原典＋注解库，在相同模型、生成约束、输出预算下对比。反映整个知识升级的收益，不单独声称检索算法提升。
2. **检索／Agent 收益：**固定同一份新语料，先比较精确检索、精确＋词面检索，再比较固定 Workflow 和允许补检索的 Agent。保持生成、校验、重试预算一致，记录工具引起的额外证据和调用。

现有评测脚本的固定证据分支与 Agent 分支并未完全复用相同修复流程，正式单模块对照前需对齐。脚本中的 `followup` 场景也不能代替完整多轮会话评测。

主要指标：目标证据召回、指定作者／著作匹配、引用存在且逐字正确、陈述被证据支持的比例、可回答任务成功率、正确不足说明率、过度拒答率，以及每个成功任务的总 tokens／调用数和耗时。引用真实性与语义支持分开评分；开放式比较可以有多个合理证据集合，不规定唯一措辞。

先做不调用模型的解析与检索验证，再用少量开发样例试跑真实模型；按实际用量配置调用／token 上限。冻结题目、语料与配置后再跑留出集，保存失败与超时。人工评分检查观点归属和关键结论是否被引文支持，不能把模型辅助评分写成已完成的人工复核。

**8. 本轮建议的完成边界与价值**

一个适合作为第二项目的知识升级版本，应当能稳定演示：

- 程序计算得到卦象，首次解读引用可定位的原典。
- 追问某一注家对某爻的解释，Agent 真实调用检索工具，返回相应著作的证据。
- 请求比较两家解释，系统区分观点归属；缺少某家材料时明确范围。
- 简繁表达和出处查询能够找到材料，引用卡可以展开查看版本与原文。
- 同卦多轮保持状态，升级知识库后旧会话引用仍可复查。
- 用冻结样例说明哪类问题有收益、哪些仍失败，以及额外检索的成本。

最值得写进简历的能力是：**领域文本的层次化建模、确定性对象与知识锚点对齐、元数据约束检索、受控补检索、引用与归属校验、可复现的对照实验**。这些能力比“导入多少本书”或“接入几个框架”更能说明工程和算法判断。

达到上述闭环后再根据错误分布决定下一步：如果问题集中在现代口语找不到对应概念，再试语义召回；如果集中在作者错标或缺文，继续修数据；如果固定取证已经足够，则限制 Agent 的启用范围。当前不扩大八字、多 Agent、知识图谱或微调范围。

**9. 本次尚未完成、实施时需核实的事项**

- 候选全文的完整性、影像与电子文本是否同版，以及所有歧义段落的作者归属。
- Kanripo 具体数据的再发布条件；现代第三方解释的具体授权范围。
- 各来源稳定的批量获取方式及完整快照构建；网页可读不代表采集链路已验证。
- 新索引与证据预算的实际效果；本方案没有给出未经运行的提升数字。

这些事项通过来源登记、小样解析、审查记录和开发集验证逐项消除；不以增加框架或扩大数据量替代。
